# Webhook Queue Service

Небольшой сервис на Flask, который идемпотентно принимает webhook-события и
обрабатывает их собственной очередью в SQLite.

## Требования

- Python 3.11+

## Установка и запуск

PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[dev]"
flask --app webhook_service:create_app init-db
flask --app webhook_service:create_app run
```

В отдельном терминале запускается worker:

```powershell
.\.venv\Scripts\Activate.ps1
flask --app webhook_service:create_app worker
```

Однократная обработка одной готовой задачи:

```powershell
flask --app webhook_service:create_app worker --once
```

Пример запроса:

```powershell
Invoke-RestMethod -Method Post -Uri http://127.0.0.1:5000/webhook `
  -ContentType "application/json" `
  -Body '{"event_id":"abc-123","type":"payment_succeeded","payload":{"amount":1000}}'

Invoke-RestMethod http://127.0.0.1:5000/stats
```

База по умолчанию создаётся в `instance/events.sqlite3`.

## Тесты

```powershell
python -m pytest
```

Тесты проверяют идемпотентность webhook, валидацию, успешную обработку,
нарастающую паузу между попытками, окончательный `failed`, восстановление после
падения worker, конкурентный захват, `skipped` для неизвестного типа и
статистику.

## Принятые решения

### Атомарный приём webhook

`events.event_id` имеет `UNIQUE`-ограничение. Событие и соответствующая задача
создаются в одной транзакции `BEGIN IMMEDIATE`. Повторный запрос получает `200`
со статусом `duplicate`, но не создаёт ни событие, ни задачу.

### Очередь и конкурентные worker

Очередь хранится в таблице `jobs`. Worker в короткой write-транзакции выбирает
готовую задачу и устанавливает ей аренду `locked_until`. `BEGIN IMMEDIATE`
сериализует конкурирующие записи SQLite, поэтому два worker не могут одновременно
забрать одну задачу.

Статус `processing` намеренно не добавлен: условие задания перечисляет четыре
статуса. Взятая задача остаётся `pending`, а наличие активной аренды означает,
что другой worker её временно не видит.

### Повторные попытки и защита от вечного pending

Номер попытки увеличивается при получении аренды. После ошибки задача снова
становится доступной через `1`, затем `2` секунды. Третья ошибка переводит её в
`failed`.

Если процесс worker завершится аварийно, аренда истечёт и задача снова станет
доступна. Если процесс упал во время третьей попытки, следующий цикл worker
переведёт задачу в `failed`, а не оставит её в `pending` навсегда. Как и любой
внешний worker, процесс должен быть перезапущен системным менеджером; без
работающего процесса очередь физически не может продвигаться.

### Детерминированная имитация ошибок

Случайные падения сделали бы тесты нестабильными. Поэтому payload может содержать
`{"simulate_failure": true}` для постоянной ошибки или
`{"fail_until_attempt": 1}` для сбоя только первой попытки. Неизвестный тип
события получает `skipped`.

### Валидация и безопасность

Тело ограничено 64 KiB. API требует JSON-объект, непустые `event_id` и `type`,
а также объект `payload`. SQL-запросы параметризованы, внутренние исключения не
возвращаются клиенту, а текст ошибки обработчика обрезается перед сохранением.
Авторизация и проверка подписи webhook не добавлялись по условиям задания.

## Ограничения

- SQLite подходит для небольшого сервиса, но сериализует конкурирующие записи.
- Заглушка обработчика не выполняет внешних побочных эффектов. В production
  реальные обработчики должны быть идемпотентными, потому что процесс может
  упасть после побочного эффекта, но до фиксации `success`.
- Аренда не продлевается во время обработки. Для долгих production-задач нужен
  heartbeat либо аренда, гарантированно превышающая timeout обработчика.
- Нет миграций, Docker, авторизации и deployment — они явно исключены из задания.
